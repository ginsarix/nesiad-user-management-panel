# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

NESIAD (Nevşehir Sanayici ve İş İnsanları Derneği) member management panel: an internal tool for 2–3 staff replacing an Excel sheet. UI text is Turkish; code, comments, and commits are English. See `AGENTS.md` — Next.js 16 differs from older versions; check `node_modules/next/dist/docs/` before writing Next code.

## Commands

Use pnpm (there's a `pnpm-lock.yaml`).

```bash
pnpm dev                        # Next dev server (Turbopack) on :3000
pnpm build && pnpm start        # production build (start warns about standalone output; it still works. Deploys run .next/standalone/server.js, see docs/deploy.md)
pnpm lint                       # biome check (skips src/components/ui/*, vendored shadcn; CI requires it to pass)
pnpm exec biome check --write <paths>   # format + fix specific files
pnpm exec tsc --noEmit          # typecheck
pnpm test --run                 # all tests (vitest)
pnpm test --run audit-logs      # tests whose path matches a pattern
pnpm db:push                    # apply src/db/schema.ts to the development database
pnpm db:generate                # write the migration for a schema change into drizzle/ (commit it; CI fails without it)
pnpm db:seed                    # create the default admin from DEFAULT_ADMIN_* if missing (sends a real verification email); the server also does this at every start
```

- Always run tests through `pnpm test`: it preloads `.env` (`dotenv/config`). Plain `vitest` fails on env validation.
- Tests run against the real development database from `DATABASE_URL`. Test records are named `__test__…` and removed in `afterAll`; audit rows they cause are removed once by `src/test/global-teardown.ts`. Test files run in parallel, so never assert on whole-table counts or reuse unique names (sector names are unique) — scope assertions to the test's own records.
- Tests always run in SMS dry run: `vitest.config.ts` sets `SMS_DRY_RUN=true` in every test worker, over the local `.env` (which may say `false`), and `src/lib/sms/netgsm.test.ts` fails if that stops holding. In dry run login codes go by email, so tests that log in mock `@/lib/mail`; tests that check what an SMS says mock `@/lib/sms/netgsm`. The same config forces `FAKE_2FA=false`, so a development `.env` with fake login codes doesn't break the login tests (`src/lib/fake-2fa-off.test.ts` checks it; `fake-2fa.test.ts` turns it back on for itself).
- Schema changes: `db:push` on the development database, then `db:generate` for the migration that production gets (the deploy runs `db:migrate` over an SSH tunnel, see `docs/deploy.md`). Don't run `db:migrate` on the development database: push built it, so the migrations would try to create existing tables. When push or generate stops with `missing_hints` (e.g. rename vs. create), rerun with `--output json --hints '[…]'`. Never edit or delete a migration that production has run; write a new one. Development data is disposable, production data isn't: when a change would lose or break existing rows (drop, rename, type change, new required column), put the conversion in the migration's SQL.
- **Destructive schema changes need a decision first.** Once a migration is merged to `main`, CI applies it to production with no prompt and no undo. Before generating a migration that drops or renames a table or column, changes a column's type, or adds a required column to a table with rows, tell the user what production data it touches and how it's handled (conversion SQL, a rename hint, or deploying when nobody is using the panel). Point it out again in the summary of the change. Never let one through silently.
- After adding or moving pages, `pnpm exec next typegen` regenerates the `PageProps<"/route">` types.
- **Release notes go with every change staff would notice.** Add its entries to `RELEASE_VERSIONS` in `src/lib/release-notes.ts` in the same change: Turkish, one plain sentence each, the page and button names staff see, typed Yeni / İyileştirildi / Değiştirildi / Düzeltildi / Silindi. Docs, tests, refactors, dependency and CI changes get none. Date the version the day it's pushed to `main` and check the date before pushing. Never add to a version that has been deployed: a later push the same day is a new version with the same date and the next `revision` (shown "V2", "V3"…), so everyone who saw the first notice gets the new one. A version's id never changes once shipped.

## Architecture

**Next.js App Router, Node runtime only, no server actions.** `src/app/(panel)/*` are the logged-in pages (shell in `(panel)/layout.tsx`, sidebar items in `src/lib/nav.ts`); `src/app/(auth)/*` are login, forgot/reset password, and `/welcome`. `/uyelik` (the public application form, `src/app/(public)/`) and `POST /api/applications` are the only routes that need no session; everything else is the panel. `src/proxy.ts` only checks that a session cookie exists; pages call `requireSession()` (`src/lib/session.ts`) and the API checks the session for real.

**API: one Hono app** at `src/app/api/[[...route]]/` (`app.ts` mounts the route files). Its middleware returns 401 without a session and puts the session in the context (`AppEnv` in `env.ts`; `actorOf(c)` gives the audit actor). better-auth has its own handler under `/api/auth`. The browser and server talk to Hono through the typed RPC client `src/lib/rpc-client.ts`; the calls live in `src/lib/fetches/*` (one file per entity), which throw the API's `{ error }` message.

**Data fetching pattern** (every list/detail page): the server `page.tsx` prefetches into TanStack Query with `queryClient.query({ queryKey, queryFn: () => fetchX(await forwardedRequestOptions()) })` and wraps the client component in `<HydrationBoundary state={dehydrate(queryClient)}>`; the client component calls `useQuery` with the same key. Don't fetch data directly in server components. Mutations invalidate every query key whose page shows the changed data (e.g. member changes also invalidate `["sectors"]` and `["companies"]`).

**Validation:** `src/lib/zod-schemas/*` has separate API schemas (dates as `yyyy-aa-gg`, blank text → `null`, multipart strings) and form schemas (dates as `gg.aa.yyyy` as typed). Forms use react-hook-form + `zodResolver` (not TanStack Form). Dates are Postgres `date` columns; convert with `src/lib/dates.ts`. Turkish-aware sorting/search uses `compareTr` / `foldTr` from `src/lib/turkish.ts`.

**Auth: better-auth** (`src/lib/auth.ts`) with the admin plugin. There are no roles: every account has role `admin` (`defaultRole: "admin"`) and can manage the others. Sign-up is disabled; accounts are created from the Panel Kullanıcıları page and get an emailed verification link that logs them in once and lands on `/welcome` (custom plugin `src/lib/auth-plugins/initial-password.ts`). Use better-auth's own endpoints wherever they cover a need; panel-user changes go through `better-auth/client` admin calls (`src/lib/fetches/panel-user.ts`), except creating an account and changing its phone, which go through `/api/panel-users` because the number must be SMS-verified first. Every account has a phone (`user.phone` is NOT NULL); login codes (better-auth `twoFactor` OTP) go to it by SMS and fall back to email when the SMS fails or on request. The client IP is read only from `x-real-ip`, set by the Plesk nginx front end. Sessions end after 30 minutes without use (`src/lib/session-idle.ts`): `SessionTimeout` in the panel layout reports typing/clicking/scrolling at most once a minute through better-auth's `get-session`, the only call that extends a session, since it alone can renew the cookie; server-side `getSession` calls pass `disableRefresh: true` (send no `disableRefresh` to extend: better-auth reads `"false"` as true). When the session is gone the tab goes to `/login?idle=1`, past any unsaved-changes guard.

**Audit log (Denetim Kayıtları) is append-only and mandatory for changes:**
- What counts as a change: anything to the association's data (members, money, lists, groups), to settings and templates, to accounts, or to what gets sent and to whom (e.g. a panel user's tahsilat notice switches). A person's own panel state isn't logged even when it's saved through the API: which release notes they've seen, and things like saved filter combinations or column choices. That state changes only how the panel looks or behaves for them. If unsure, ask.
- Every Hono mutation writes `recordAudit(tx, …)` (`src/lib/audit.ts`) in the same transaction as the change, with `actorOf(c)`. Updates store field-level changes as display strings built with `diffFields` / `change` from `src/lib/audit-diff.ts` (only fields present in the update; write nothing when nothing changed). Creates and deletes store the whole record in `details`; deletes read related data (links, names) before deleting. **Exception:** a public application submission writes no audit entry, and the applicant-side fields (TC number, birth place, education, gender, reference, other associations, identity document, consent, Ret Notu, and the company's employee count, website, company intro and activity document) never have their values written to `details` or `changes`; staff edits to them record only the field label with "•••" (`diffRedacted`). Name, email, mobile, birth date, notes, PO card and photo are logged plainly (user decision 2026-11-27). Decision entries record each notice channel's outcome, never the address, number or text.
- Logins, logouts, password events, and panel-user actions are recorded by the better-auth plugin `src/lib/auth-plugins/audit.ts` (failures there are logged, never block auth); password resets come from `onPasswordReset` in `auth.ts`. Panel Kullanıcıları' Son Giriş Tarihi is read from these rows (newest `login` / `login_email_link`, `GET /api/panel-users/last-logins`), not stored.
- Labels for new actions go in `src/lib/audit-labels.ts`.

**Tables** use TanStack Table v9 (`useTable`, `tableFeatures`, `createColumnHelper` — not the v8 API; the bundled skills in `.claude/skills/pnpm-@tanstack+react-table-*` are authoritative). Every table has the "Sütunlar" column toggle (`src/components/column-toggle.tsx`) with visibility stored in a cookie: the page reads it with `getSavedColumnVisibility(tableId)` and passes it to `usePersistedColumnVisibility`, so the server renders the right columns. Shared pieces: `SortableTableHeader`, `SearchCombobox` (Turkish-aware searchable select), `info-fields.tsx` (`orDash`, `formatDate`, `PassiveTag`, `InfoFields`). List filters are mirrored into the URL with `history.replaceState`, and `rememberListSearch` / `listHref` (`src/lib/list-href.ts`) make "… dön" links return to the same filtered list.

**UI:** shadcn `base-nova` style on Base UI (not Radix): `render` props instead of `asChild`, `Select` takes an `items` prop. Add components with `pnpm dlx shadcn@latest add <name>`, declining overwrites of existing files. Company logos are stored in `UPLOAD_DIR` (default `uploads/`, gitignored) and served by the authenticated `/api/files/:filename` route. `company.logo` is always a raster image: a PDF or SVG logo is drawn to a trimmed PNG in the uploader's browser (`src/lib/logo-upload.ts`; pdf.js loaded only when a PDF is picked, SVG drawn through an `<img>` so its scripts never run) and sent with the original, which is kept in `logo_original`. The server never parses PDFs or SVGs (it only checks their contents are one, `storeLogoOriginal`) and serves `.svg` files with a CSP sandbox; keep pdf.js out of modules the server imports (`src/lib/fetches/*` take a ready `LogoUpload`). Member photos (`member.photo`, so staff recognize faces) are stored and served the same way, but the browser shrinks every pick to an 800px JPEG on white as soon as it's picked (`src/lib/photo-upload.ts`, which also applies EXIF rotation and drops the metadata), no original is kept, and the server only checks the contents are JPEG/PNG. People show as round `MemberAvatar`s wherever a member's name is listed; company logos (`CompanyLogo`) stay square. A page that holds unsaved changes calls `useNavigationGuard` (`src/lib/navigation-guard.ts`): it stops link clicks to other pages and the logout button (`navigationBlocked()`), and asks before a reload; the Ayarlar → Bildirimler tab is the example (save bar at the bottom right, shakes when leaving is stopped).

## Domain notes

- Members (üyeler) are people: name (Adı/Soyadı), contact, photo, PO card, notes and the application fields, with zero or one company (`company` table, `member.company_id`). A company can belong to several members. There is no Firmalar page: a company is seen and edited only inside a member's Firma section (none / existing / new); editing a shared company warns and changes it for every member on it, and a company left with no members is deleted (audited). Görev (`company_role`) is the member's role at the company. Members are hard-deleted; the audit log keeps the deleted record. Their `status` is `active` (Aktif), `passive` (Pasif), `candidate` (Aday) or `rejected` (Reddedildi); lists default to Aktif. Aday and Reddedildi are applications from `/uyelik`: they are left out of Aktif lists, sector counts, the member pickers and SMS, and only the decision actions (Kabul Et → Aktif, Pasif olarak ekle → Pasif, Reddet → Reddedildi, Tekrar Aday yap → Aday, `POST /api/members/:id/decision`) move a member out of them. Reddet takes an optional Ret Notu (`rejection_note`): staff-only, never sent to the applicant, shown only while Reddedildi, cleared by Tekrar Aday yap, and redacted ("•••") in the audit log. It is a rejection note, not a general member notes field. The applicant gets an email and SMS from editable templates (Ayarlar page, Bildirimler tab) when the application is saved ("Başvurunuz alındı", not awaited, no audit entry) and, after commit, on Aday → Aktif and Aday → Reddedildi (audited as `application_notice`); no other move sends anything. Kıdem is computed from Üye Giriş Tarihi ("5 Yıl", "10 Yıl"…), not stored.
- Genel Bakış (`/`, `src/app/(panel)/page.tsx`) is the landing page after login: a dashboard of things needing attention (Aday applications, the next 7 days' celebrations, automatic SMS that didn't go out), this calendar year's money, membership breakdowns and the latest 3 audit entries, all from one `GET /api/dashboard` (`dashboard.ts`; pure helpers in `src/lib/dashboard.ts`). Money is summed in Postgres like everywhere else. "Bu yıl tahsilatı olmayan aktif üyeler" is not a dues/aidat debt list (there is no expected-dues concept). "Yıllara göre yeni üyeler" counts only current members, since leaving isn't recorded. The only chart library is Recharts via shadcn `chart` (the monthly chart); other bars are plain HTML.
- Sürüm Notları (`/release-notes`) is the staff changelog, read straight from `src/lib/release-notes.ts` (no API): search, type chips and a "Sürümler" jump list, linked from the small "Sürüm …" line pinned to the bottom of the sidebar (`footerLinks` in `nav.ts`). Each version is one production deploy; the history before 2026-11-24 was rebuilt by deploy day from git. `NewVersionDialog` in the panel layout shows each person the versions they haven't seen, once: `user.release_notes_seen` holds the id of the newest one they've seen (null → only the newest counts as unseen; an id not in the list goes by its date and revision: newer than the list (rollback) → nothing, older (its version was removed) → the versions after it; new accounts start at the newest via the create hook). Closing the dialog in any way or opening `/release-notes` calls `POST /api/release-notes/seen`, which writes the newest id from the running code. Not audited (own panel state). Unseen is decided by list order, never by comparing id strings.
- `docs/could-have.md` lists "could have, but no rush" ideas. When the user defers something that way, add it there; when one gets built, remove it.
- Yetkililer no longer exist: the 2026-11-27 migration converted them to members. `representative_member_map` maps old yetkili ids to members and backs the `/representatives/:id` redirect. The old `authorized_representative` and `members_representatives` tables and the legacy company columns on `member` (`legacy*` in `schema.ts`) are unused and dropped by the scheduled cleanup PR (`cleanup/drop-yetkili-legacy`, merged by `.github/workflows/scheduled-cleanup.yml`); new code must never read or write them.
- Sectors are a managed list (Sektörler, on the Parametreler tab of the Ayarlar page, `/settings`) referenced by id; names are unique ignoring Turkish case (`name_key`). Deleting a sector sets members' `sector_id` to null.
- The same tab has three name-only lists, kept in one `parameter` table keyed by `kind` (`src/lib/parameters.ts`): Tahsilat Türü / Ödeme Türü say what the money is for (how it moves is its Kasa - Banka; the Tipi lists were removed for it), and Dernek Görevleri (`association_role`) is the Görev on the Organizasyon pages; it is not the member's Görev at their company. Names are unique per list, ignoring Turkish case. An entry used by a payment, tahsilat or Organizasyon row can't be deleted (409 with the count, `usageCount` in the list); renaming is fine.
- Organizasyon (sidebar parent): Yönetim, Komiteler, Disiplin Kurulu, Denetim Kurulu, Onur Kurulu. Each page lists named groups (İsim, unique per page ignoring Turkish case), and a group holds rows of member + Dernek Görevi (`member_id`) in the order entered. The same member may appear in a group more than once. There are no terms or current/past flags: staff edit a group or add another, the panel takes no position. Each page has its **own tables** (`committee` + `committee_member`, …) on purpose, because staff may want one handled differently later. For now they share everything else: the config in `src/lib/organizations.ts`, one Hono route `/api/organizations/:organization` (slug), `src/lib/fetches/organization.ts`, and one set of pages under `src/app/(panel)/organization/[organization]/`. To special-case one, branch on the organization or give it its own static route folder (Next.js prefers it over the dynamic one). New rows need an Aktif member; a Pasif one is kept only if already in the group. Deleting a member removes their rows (cascade, named in its audit entry); a Dernek Görevi in use can't be deleted. Each page audits under its own entity type. The member details page lists the member's groups, and the member form edits them too (Organizasyonlar section, rows of Organizasyon › Grup › Dernek Görevi, sent as `organizations`; `member-organizations.ts`). Unlike the group form, which replaces a whole group, it touches only the member's own rows: a kept row (`rowId`) keeps its place, a new or moved row goes to the end of its group, and each changed group gets its own audit entry besides the member's "Organizasyonlar" change. A `rowId` that's gone (someone saved the group meanwhile, which renumbers its rows) refuses the save with 409.
- Kasa - Banka (`cash_account`, `/cash-accounts`, first under Finans) is one list of cash boxes and bank accounts: İsim (unique ignoring Turkish case, `name_key`) and Aktif/Pasif. Every ödeme and tahsilat has a required Kasa - Banka, picked in its own "Kasa - Banka" section under the form (links to the account); a new record needs an Aktif one, an edit keeps its own even if Pasif (`usableCashAccount`). An account with ödemeler or tahsilatlar can't be deleted (409 with the counts; make it Pasif). Money between accounts (virman) isn't recordable yet (`docs/could-have.md`).
- Kasa - Banka dönemleri (`cash_account_period`): staff create each account's periods (at least one) with a start date (may be in the future) and a Başlangıç Bakiyesi, in the form's Dönemler section (rows keep their `id`; PATCH replaces the list, an unknown id is a 409; a PATCH without `periods`, like Pasife al, leaves them alone). A period runs to the day before the next one's start; the last is open-ended. Records aren't linked to a period: their date decides it (`periodIndexFor`, `src/lib/cash-account-periods.ts`). Each period's Bakiye = its Başlangıç Bakiyesi + tahsilatlar − ödemeler dated in it, never stored, summed in Postgres on read (`selectPeriodBalances`, `cash-account-queries.ts`). The account's Bakiye (list, header, Genel Bakış) is the current period's: the latest one started by today, null ("—") if none has. Records dated before the first period are allowed (staff's call), count in no Bakiye, and the details page says so with links. Start dates are unique per account, checked by the API under a lock on the account row (`for update`), not a constraint, so an edit can swap two dates. Balances never flow forward on their own: Devir (`POST /api/cash-accounts/:id/carry-over`, the "Devir" box on the details page, audited as `carry_over` every time) sets a later period's Başlangıç Bakiyesi to an earlier one's current Bakiye and remembers the source and amount (`carried_from_period_id` / `carried_amount`), so a period tab warns when the source has changed since and offers "Tekrar devir et". The link is dropped when its Başlangıç Bakiyesi is typed by hand, the source stops being earlier, or the source is deleted. The details page has one tab per period (opens on the current one) with its figures and the Tahsilatlar/Ödemeler dated in it; "Ekle" from there passes `?cashAccount=` and returns there. The ödeme/tahsilat form's Kasa - Banka section shows the Bakiye of the typed date's period and warns, without blocking, when the date is before every period.
- Cariler (`counterparty`, `/counterparties`) are who the association pays. The table is named neutrally only to keep it open whether tahsilatlar will use it too; that's undecided, so ask rather than assume. Ünvan is unique ignoring Turkish case (`title_key`). Şehir/İlçe are stored as names from the vendored province/district list in `src/lib/turkey/` (MIT, from turkey-neighbourhoods; update by copying its `src/data/` files); the API checks the district belongs to the province. A cari with payments can't be deleted.
- Ödemeler (`payment`, `/payments`): cari, amount, date (not in the future), Ödeme Türü (the API checks it is from the right list), Kasa - Banka, note. Amounts are `numeric(12,2)` and travel as strings (`"1250.50"`); never add money as JS numbers. Per-row aggregates (a cari's Toplam Ödenen, a proje's Toplam Tahsilat, the Genel Bakış money) are summed in Postgres (`sumOfAmounts` / `sumOfCollected`). Every table with an amount column (Ödemeler, Tahsilatlar, Cariler, Projeler, Kasa - Banka, and the Ödemeler/Tahsilatlar tables on detail pages) ends in a pinned "Toplam" row, `TableTotalFooter`, which the browser sums from the rows shown with `sumAmounts` (BigInt kuruş); the toolbar's "N ödeme · Toplam X" is summed the same way. The list APIs send no `total` (the user's call, so don't move it back to Postgres), and the Excel export sums its Toplam row from the same rows with `sumAmounts`. Typed amounts are Turkish ("1.250,50") and parsed/shown with `src/lib/money.ts`. List filters run on the server (`selectPayments`), so the list and the Excel export share one query.
- Tahsilatlar (`collection`, `/collections`, Finans menu): money collected from a member (`member_id`; the member is the person, and a tahsilat records no firm), with Tahsilat Türü, Kasa - Banka, amount, date, note and an optional proje. A new tahsilat needs an Aktif member and an Aktif proje; editing keeps the ones it already has even if they've become Pasif. The form's Proje section is none / existing / new; "new" creates the proje (`insertProject`) in the same transaction, so a failure saves neither. Member pages list their tahsilatlar, and a member with tahsilatlar can't be deleted (409 with the count; the page suggests Pasif instead). The money, filter and export rules are the same as Ödemeler (`selectCollections`, filter `project=none` for Projesiz).
- A new tahsilat notifies the member (email to E-posta, SMS to Cep Telefonu) and every other active panel user (not the recorder, not disabled accounts) by email and SMS, from editable templates (Ayarlar page, Bildirimler tab, `collection_notice_settings`). The Kasa - Banka name is `{kasa}`; the default texts use it only in the staff notices, so account names stay internal unless staff add it to the member's. The member's name is `{uye}` (was `{yetkili}`). It runs after the response (`notifyCollectionCreated`, not awaited) and is audited as `collection_notice` with outcomes only. Each panel user has two switches, Tahsilat SMS'i and Tahsilat E-postası (`user.collection_sms` / `collection_email`, on by default, flipped from the Panel Kullanıcıları row menu through `PATCH /api/panel-users/:id/collection-notices`, audited as `panel_user` / `collection_notices`); someone with one off gets nothing on that channel and isn't counted in the outcomes. Account messages (login codes, verification) ignore them. Edits and deletes send nothing. Tests that create tahsilatlar through the route must mock `@/lib/mail`.
- Projeler (`project`, `/projects`): Ad, Proje Numarası (unique ignoring Turkish case and spaces, `number_key`) and Aktif/Pasif. A proje with tahsilatlar can't be deleted; make it Pasif instead.
- Taahhütler (`project_pledge`) are a record of what a member pledged to a proje: rows of Üye, Adet and Tutar (per unit), with each row's Toplam and a Genel Toplam. They are only a record, not linked to tahsilatlar. They're edited on the proje create/edit forms (sent as `pledges` with the proje; a PATCH without `pledges` leaves them alone) and in place on the details page (`PUT /api/projects/:id/pledges`, save bar + `useNavigationGuard`), all through `PledgesEditor`. Its "Adet ve tutarı tüm satırlara uygula" checkbox (not saved, unticked on load) spreads an Adet or Tutar typed in one row to every row via `setValue`; while ticked, Cmd/Ctrl+Z / Cmd/Ctrl+Shift+Z / Ctrl+Y undo and redo whole spread steps (`src/lib/spread-history.ts`, one step per box until it blurs, keyed by row id), since the browser's own undo would only revert the one box and spread that. A row added while ticked copies the last row's Adet and Tutar. Every save replaces the rows and audits one "Taahhütler" change. Totals are never stored or returned: `src/lib/pledges.ts` computes them on the fly in BigInt kuruş (the "sum in Postgres" rule is for server-side aggregates). New rows need an Aktif member; a Pasif one already saved stays. The rows go with a deleted proje; a member with taahhütler can't be deleted (409, same as tahsilatlar).
- Tahakkuk (`accrual`, `/accruals`, last under Finans) is one association-wide list of rows Üye | Tahakkuk Türü | Tutar, not tied to anything and edited in place on its page (`GET`/`PUT /api/accruals`, `AccrualRowsEditor`, `SaveBar`). Staff chose one list over separate tahakkuk records to avoid create/edit back-and-forth, and a per-row type over Adet. Tahakkuk Türü (first labeled Aidat) is required and picked from the Tahsilat Türü list (`collection_category`); a Tahsilat Türü used by a row counts in its usage and can't be deleted. There is no Toplam column; Genel Toplam is the sum of Tutar (`typedAccrualTotal`, `sumAmounts` in kuruş). Since everyone edits the same list, a save carries the `version` (hash of the rows) the page started from and is refused with 409 if someone saved in between; the page keeps the edits, İptal returns to the latest saved list. New rows need an Aktif member (`member-rows.ts`, shared with Taahhütler). Audited as `accrual` / update with one "Tahakkuk" change. A member with tahakkuk rows can't be deleted. Its tests (`accruals.test.ts`) keep and restore the dev list, and every test touching the table lives in that file so they never run in parallel. It is not an expected-dues/aidat-debt concept and isn't linked to tahsilatlar.
- "Otomatik Tahsilatlar" (the "yakında" sidebar item, placeholder href `/automatic-collections`) is a separate idea staff are still thinking through. It is not Tahsilatlar; don't merge or rename them.
- Excel export (`GET /api/payments/export`, `/api/counterparties/export`, `/api/collections/export`) is built on the server with `write-excel-file/node`: real date and number cells, frozen header.
