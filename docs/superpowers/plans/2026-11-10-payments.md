# Ödemeler and Cariler Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let staff record the association's payments (Ödemeler) to a managed list of payees (Cariler), filter and total them, and export both lists to Excel.

**Architecture:** Two new Postgres tables (`counterparty`, `payment`) behind two Hono route files, each mutation audited in its transaction. Payment filters run on the server so the list, its total and the Excel export come from one query function. The UI follows the Yetkililer pattern: server prefetch + TanStack Query, TanStack Table v9 lists, page forms with react-hook-form.

**Tech Stack:** Next.js 16 App Router, Hono RPC, Drizzle + Postgres, zod 4, TanStack Query/Table v9, react-hook-form, `write-excel-file` (new dependency, Node entry `write-excel-file/node`), `read-excel-file` (new dev dependency, tests only).

**Spec:** `docs/superpowers/specs/2026-11-10-payments-design.md`

## Global Constraints

- UI text is Turkish; code, comments and commits are English. Read `CLAUDE.md` first; Next.js 16 differs from older versions (`node_modules/next/dist/docs/`).
- Use `pnpm`. Run tests only through `pnpm test --run <pattern>`. Tests hit the real dev database: name records `__test__…` plus a random suffix, delete them in `afterAll`, and never assert on whole-table counts.
- Schema changes: `pnpm db:push`, then `pnpm db:generate --name <name>`; commit the migration. Never run `db:migrate` locally. Every migration here only creates tables and foreign keys.
- Every mutation calls `recordAudit(tx, …)` in the same transaction with `actorOf(c)`. Creates and deletes store the whole record (`describeFields`); updates store only changed fields (`diffFields`/`change`) and write nothing when nothing changed.
- Money is never a JS float in storage or totals: `numeric(12,2)` column, amounts as strings like `"1250.50"` over the API, totals summed in Postgres. Only the Excel cell and on-screen formatting convert to `Number`.
- Amounts display as `₺1.250,50`. Dates are typed `gg.aa.yyyy` and travel `yyyy-aa-gg`.
- Ünvan is unique ignoring Turkish case (`title_key = title.toLocaleLowerCase("tr")`).
- A cari, Ödeme Türü or Ödeme Tipi used by a payment can't be deleted (FK `on delete restrict` + a 409 with the count).
- Excel export: real date and number cells, bold frozen header, file `odemeler-yyyy-mm-dd.xlsx` / `cariler-yyyy-mm-dd.xlsx` (Istanbul date). Payments newest first, cariler by Ünvan. Exports aren't audited.
- Province/district data is vendored from muratgozel/turkey-neighbourhoods (MIT) with its license; no npm package.
- `pnpm lint` and `pnpm exec tsc --noEmit` pass at the end of every task.

## Review Focus

1. **A cari renamed after payments were made.** The payments list, export and audit labels show the new title. Covered by the list reading titles through a join (Task 3 test "shows the current cari title").
2. **Amount typed with Turkish separators** ("1.250,5", "1250", "0,99", "1,250.50", "-5", "0"). The first three parse; the rest are rejected with "Geçerli bir tutar girin" or "Tutar sıfırdan büyük olmalı". Tests in Task 1 `money.test.ts`.
3. **Kuruş totals** like 0.10 + 0.20 must show 0,30, not 0,30000000000000004. Covered by Task 3 "sums kuruş exactly" and Task 4's total row.
4. **Changing Şehir after picking İlçe** in the cari form leaves a district from the old province. The form clears İlçe when Şehir changes, and the API rejects a district outside its province (Task 2 test "rejects a district of another province").
5. **A payment whose Ödeme Türü id points at an Ödeme Tipi (or a Tahsilat entry).** The API rejects it with 400 (Task 3 test "rejects a parameter from the wrong list").
